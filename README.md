## Development on another computer

Use Node.js 22.13 or later, with the built-in `node:sqlite` module. There are no third-party npm dependencies in the retained app. From `project/`, run:

```text
node tools/check-access.mjs
node tools/check-kitchen.mjs
node tools/build-worker.mjs
node tools/build-local-trial.mjs
node tools/export-kitchen.mjs
```

The last two build commands write the standalone HTML and kitchen JSON one directory above `project/`. Keep that directory structure. The supplied standalone file is already built.

The shared frontend's editable source is `dist/index.html`, despite its folder name. Do not delete `dist` as disposable output. Edit the backend in `worker/server-template.js`; `tools/build-worker.mjs` generates `worker/index.js` and `dist/server/index.js`. Edit local-only additions in the `tools/local-*.js` files. The project is not a React/npm scaffold; do not initialise another project over it.

## Current deployment contract

This is a Cloudflare Worker-compatible ESM module with a default `fetch(request, env)` export. The entrypoint is `dist/server/index.js`. It requires a D1 database bound as `DB`. `drizzle/0000_shared_trial.sql` contains the users, app_state and audit_events schema; migration metadata is included. Preserve applied migrations. Build the Worker after shared-source changes. The handover preparation includes the migration under `dist/.openai/drizzle/` for packaging, but future builds must restage updated migration files when needed.

`.openai/hosting.json` identifies the EXISTING Sites project. Its identifier is configuration, not a password. Deploying to that project requires authorised editor/owner access; an app Manager role or visitor invitation does not give deployment rights. Linh must use her own authorised account. Do not create a replacement Site or overwrite an existing deployment simply because this archive contains its project ID. Use the installed Sites workflow for that existing Site, after reviewing the outstanding issues and backing up live records.

The current backend trusts identity headers supplied by the Sites gateway. It does not verify independent passwords or authentication tokens. DO NOT expose this Worker directly on another public host with client-supplied identity headers; callers could impersonate staff. Before moving hosting, implement a trusted authentication layer with verified sessions, session revocation, account recovery and server-side roles. Independent Bay email login has not been implemented.

A fresh database has no users. The revised backend intentionally rejects unknown users and no longer makes the first visitor a manager. Provision the initial manager through an authorised database administration process tied to the chosen authentication system. Never enable unauthenticated self-enrolment as a workaround.

## Records and backups

Live stock, staff accounts and history are stored remotely and are NOT in this ZIP. A local trial's changes are in its browser storage, also NOT in this ZIP. Before any transition, export relevant records through the existing authorised app, plus an authorised full database backup where available. Preserve identity mappings, disabled-account state and attribution. Do not import old sample stock over live records.

Local trial files have manager tools without authentication and do not sync to the cloud. Their browser storage may depend on browser and file path; export a backup before moving or renaming a trial HTML. Use Data backup to import an existing local backup, then Repair kitchen headings to reclassify matching supplied products without replacing counts. Do not send sensitive production records unnecessarily.

The revised shared backend retains pre-save recovery snapshots in the SAME database. That is not an offsite backup. Retention, independent backup storage, scheduled validation and a full recovery exercise remain required. Permission and SQLite-backed recovery checks passed locally, but end-to-end browser/iPhone, concurrency and operational testing remain outstanding.
