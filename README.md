# Bay Bellerive stock app — project status

## Start here

This started as a handover snapshot from JB to Linh and is now an actively developed project, tracked in git at https://github.com/linh-luu-bay/stock-control (`main` branch).

- `project/` contains the shared frontend, backend, database schema, and build/dev tools.
- `Bay-Bellerive-Local-Trial.html` is a standalone, sign-in-free trial build with extra kitchen features (subgroups, "details needed" markers, fractional counts) generated by `tools/local-details.js` and `tools/local-kitchen-groups.js`. These features are **not** merged into the shared server version.
- `Bay-Bellerive-Kitchen-Stocktake.json` contains the supplied 82 kitchen items, including unknown quantities and unconfirmed reorder settings. It has not yet been imported into the shared (Supabase-backed) service — it's still a standalone file.
- `project/TRIAL-READINESS.md` records unfinished work and limitations against the original 10-item trial checklist; several items are now further along than that file alone reflects (see "Current deployment contract" below), but it hasn't been fully rewritten to match.
- `project/design.md`, `project/sitemap.md`, `project/userflow.md` document the shared frontend's visual design, screen/dialog structure, and user flows, extracted directly from `dist/index.html`.
- `MANIFEST.json` lists the originally packaged handover files and checksums; it does not reflect files added since.

## Which version is which?

The original private site (`https://bay-bellerive-stock.josephbarber92.chatgpt.site/`, requiring OpenAI sign-in) has **not** received any of the work described in this file — none of it has been deployed anywhere publicly yet. Everything below currently only runs locally via `tools/dev-server.mjs`.

The shared server's storage backend has changed from Cloudflare D1 to **Supabase (Postgres, accessed over its REST API)**. `drizzle/0000_shared_trial.sql` is the old D1/SQLite schema, kept for reference only; `project/supabase/schema.sql` is the current, authoritative schema and must be run once (via the Supabase SQL Editor) against any fresh Supabase project before the app will work.

The standalone trial (`Bay-Bellerive-Local-Trial.html`) is unaffected by any of this — it still uses only browser storage and has its own separate feature set, as before.

## Authentication

The shared app now has real, independent sign-in — the earlier "trusts headers from the Sites gateway" model described in older versions of this file is gone entirely.

- Sign-in is **Google OAuth via Supabase Auth** — a single "Log in with Google" button, no password, no self-service sign-up page.
- After Google authenticates the person, the Worker verifies the session token directly with Supabase (`/auth/v1/user`) and then looks their email up in the `users` table. Only a pre-existing, active row lets them in; the row's `name` and `role` are used as-is (a Google profile name never overrides what's stored there). An email not found in `users` sees "You don't have access to this app" and is immediately signed out.
- There is no self-enrolment and no UI to add the very first account (the manager-only Accounts screen requires already being signed in as a manager). The first manager row has to be inserted directly via SQL in the Supabase dashboard — already done for `linh@barberpropertymaintenance.com` and `j.barber@barberpropertymaintenance.com`.
- Only Google is wired up in the UI today. Microsoft/Azure AD sign-in was scoped out (Google Cloud Console app + Supabase provider config steps) but the frontend button for it was never built, since the app moved to a single "Log in with Google" screen instead of a multi-provider one.

## Development on another computer

Use Node.js 22.13 or later. There are no third-party npm dependencies. From `project/`, you'll need a `worker/.env.local` file (gitignored, never commit it) with:

```text
SUPABASE_URL=...
SUPABASE_ANON_KEY=...
SUPABASE_SERVICE_ROLE_KEY=...
```

Then:

```text
node tools/check-access.mjs      # unit tests for cost redaction, event validation, etc.
node tools/check-kitchen.mjs
node tools/build-worker.mjs      # regenerates worker/index.js and dist/server/index.js
node tools/build-local-trial.mjs
node tools/export-kitchen.mjs
node tools/dev-server.mjs        # runs the real worker locally at http://localhost:8787,
                                  # talking to your real Supabase project (not a local DB)
```

`tools/dev-server.mjs` is a plain proxy — it does no identity stamping of its own. Signing in goes through the real Google OAuth flow, so whoever tests it must already be a row in the Supabase project's `users` table. Its Site URL / Redirect URL (Authentication → URL Configuration in the Supabase dashboard) must match wherever you're running it, e.g. `http://localhost:8787` and `http://localhost:8787/*`.

`node tools/check-access.mjs` no longer runs the deep role/atomicity/conflict integration suite it used to — that was written against an in-memory D1-shaped SQLite database and doesn't apply to Supabase/HTTP storage. It still covers cost redaction, event-key logic, and anonymous rejection; the Supabase-backed request paths are currently verified manually (via `dev-server.mjs` + curl), not by an automated suite.

The shared frontend's editable source is `dist/index.html`, despite its folder name — do not delete `dist` as disposable output. Edit the backend in `worker/server-template.js`; `tools/build-worker.mjs` generates `worker/index.js` and `dist/server/index.js` from it — edit those generated files only via the template, never directly. Edit local-only trial additions in `tools/local-*.js`. This is not a React/npm scaffold; do not initialise another project over it.

## Current deployment contract

This is still a Cloudflare Worker-compatible ESM module with a default `fetch(request, env)` export, entrypoint `dist/server/index.js`. It no longer needs a D1 `DB` binding — it needs two environment values instead:

- `SUPABASE_URL` — plain config, not secret.
- `SUPABASE_SERVICE_ROLE_KEY` — a real secret; on Cloudflare it should be set via `wrangler secret put`, never committed or left in a plain vars block.

**Nothing has been deployed to Cloudflare yet.** `.openai/hosting.json` identifies the old Sites project this handover originally targeted; that hosting path has been abandoned in favor of independent hosting + independent auth (see "Authentication" above), and a real Cloudflare Workers deployment target still needs to be chosen and set up before this can run anywhere but `localhost`.

## Records and backups

Live stock, staff accounts, and history now live in Supabase (`app_state`, `users`, `audit_events` tables — see `project/supabase/schema.sql`), not in this repository and not in D1. A local trial's changes are still only in its own browser storage.

Every successful save still creates a recovery snapshot atomically alongside it (now via the `save_app_state` Postgres function instead of a D1 batch write) — Supabase's own `audit_events` table holds the last saves; older ones remain queryable but only the most recent 30 are listed in the app's recovery picker. This is still not an offsite backup: independent backup storage, a retention policy, and a real restore exercise are still outstanding (see `project/TRIAL-READINESS.md`, item 2).

Local trial files still have manager tools without authentication and do not sync anywhere. Export a backup before moving or renaming a trial HTML, same as before.
